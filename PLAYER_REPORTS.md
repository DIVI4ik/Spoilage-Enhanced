# Player-reported defects — take these first

Three defects found by playing the mod, not by reading the code. Two are reproduced in
game; the third is a strong suspicion with the code path already traced. They are queued at
the top of `TASKS.md`. Take them in order, one per pass, before any lens-generated task.

**All three are runtime behaviour.** The unit suite cannot see any of them: a frozen HUD
timer, a container click path, and a block-eating path all exist only in a running game.
Step 5 of the loop therefore requires a real launch with a line from the fresh log — a green
suite is not proof here.

---

## 1. Freshness timer is frozen on world-generated blocks

**Symptom (player):** looking at a block that has freshness, the timer does not tick at all
if the block was generated by the world. Place the same block by hand and it counts down
normally.

**Traced cause.** `BlockSpoilageNetworking.java:74` — when the block is not tracked, the
server answers:

```java
stateOrdinal   = FRESH.ordinal();
ticksRemaining = SpoilageConfig.getInstance().getFreshDurationForItem(dropItem);
```

That is a constant. Every request recomputes the same number, so the client renders a
countdown that never advances.

World-generated blocks are never tracked: `BlockStateChangeMixin` registers only from
`Level.setBlock`, and world generation writes chunk sections directly without ever calling
it. Player placement does go through that path, which is why hand-placed blocks work.

**What to decide before coding.** The existing comment says an untracked block "will start
its life fresh the moment it is harvested". If that is the intended design, the defect is
presentational — the HUD must stop showing a moving timer for such blocks. If wild blocks
are meant to age in place, register them lazily on first query instead. Either way, the
display and the behaviour must agree; what must not survive is a timer that shows a
countdown it never performs.

Watch the cost of the lazy option: a write to `SavedData` on every glance at every wild
block is a per-look write on a path that used to be read-only.

## 2. Right-click inserts a rotten item into a crafting slot

**Symptom (player):** the mod forbids using spoiled items in crafting, but with a stack of
4 carrots where one is rotten, right-clicking still places it into the grid.

**Traced cause.** `ScreenHandlerMixin.java:132` cancels the insertion only when

```java
FoodSpoilageUtil.isEntirelyRotten(stackToInsert)
```

is true — that is, when the *entire* carried stack is rotten. The transfer, however, moves
the **worst** items first: `SlotMixin.safeInsert` calls `extractWorstItems`. So a right-click
takes exactly one item and that one is the rotten carrot, while `isEntirelyRotten` on the
4-stack answers false and the guard lets it through.

The guard asks about the wrong thing: it tests the carried stack when it should test the
slice that is about to move.

**Fix direction.** Derive the actual insert count for this click — right-click inserts 1,
left-click the whole stack, `SWAP` the whole stack — and reject when the worst-N slice for
that count contains a `ROTTEN` entry. Check the other click types in the same block while
you are there: `PICKUP_ALL` and `QUICK_CRAFT` read the carried stack through the same guard.

## 3. Suspected: a placed cake loses its spoilage entirely

**Question (player):** if a rotten cake is placed on the floor, does eating it still poison?

**Traced path — verify before fixing.** `minecraft:cake` is spoilable as an *item*:
`SpoilageConfig:741` gives it an `item_durations` entry and `AutoFoodDetector:92` lists it
among the items that spoil without being edible. But there is no `CakeBlock` handling
anywhere in `mixin/`, and `cake` is not in `tracked_blocks`.

Placing a cake therefore drops its SPOILAGE component, and eating a slice off the block
never passes through `ItemStackMixin:115-125` — the only place the rotten effects (poison,
hunger, nausea) are applied. The expected consequence: no poison, and placing then eating
launders any spoiled cake back to clean food.

**Prove it first.** Force a cake to ROTTEN, place it, eat a slice, and check the fresh log
for the effect. Record `NO_BUG` with that evidence if the effect does fire — a refuted
suspicion is a real result and closes the question.

If confirmed, **fix the class, not `minecraft:cake`.** Every block that is eaten in place
loses its spoilage the same way, and that includes modded content: `AutoFoodDetector`
already registers modded blocks generically — `scanTagsAndBlocks()` walks the whole block
registry and tracks any block whose item form is spoilable — so a modded cake is identified
and then hits exactly the same dead end.

Note the identification limit while you are here, because it decides how wide the fix has to
be. `computeIsSpoilable` says yes only via a hardcoded vanilla list (`Items.CAKE`, `EGG`,
`MILK_BUCKET`), the `FOOD` component, an explicit config entry, or the `c:foods/...` /
`CONSUMABLE` second pass. A cake-like item has no `FOOD` component — you eat the block, not
the item — which is why vanilla cake needed the hardcoded entry. A modded one is caught only
if its author tagged it. And the `name.contains("cake")` chain in `computeBaseDurations` does
**not** help: it only picks a duration for something already known to be spoilable.

So key the fix off a property every such block shares, not off a block id list. Carry the
spoilage onto the placed block, or refuse placement of a rotten one — but make it work for a
block this mod has never heard of.

  untouched, is tested on the RAW value before the multiplier, lives as a shared `NO_TIMER`
  constant on the payload instead of a bare `-1L` in two files, has its missing `ru_ru`
  translation, and is pinned by `ClientBlockSpoilageCacheTest.noTimerSentinelSurvivesBothAccessors`
  with a nonzero elapsed time. Confirmed in game by the player.

  **Why Pass 221 believed it was done:** its evidence line was "Runtime verified runClient —
  0 InjectionError". That proves the mixin loaded. It says nothing about what the HUD drew.
  A launch log is not proof for a visual defect unless it carries the rendered value.
- **§2 rotten right-click insert** — FIXED (Pass 223): new `FoodSpoilageUtil.worstSliceContainsRotten(stack, n)`; right-click (QUICK_CRAFT) uses N=1, other clicks use the whole stack. 8 tests.
- **§3 cake laundering** — FIXED (Pass 224): `GourdBlockMixin` refuses placement of a rotten block that is eaten in place (`isEatenInPlace` → CakeBlock). 5 tests. Note: the fix is keyed off `instanceof CakeBlock`, not a block id list — but a modded block eaten in place is NOT detected (it would need to register itself). The report's suggestion of a fully general property-based detection was refuted by test: pumpkin's item form has no FOOD component either (it is crafted into pie, not eaten), so "spoilable item + no FOOD component" over-matches and would refuse legitimate pumpkin placement.

## 4. Crash at bootstrap: CandleCakeBlock has no 'eat' method

**Symptom (player crash):** `InvalidInjectionException: Critical injection failure: @Inject annotation on spoilage_enhanced$readConditionBeforeBite could not find any targets matching 'eat' in CandleCakeBlock`. Game crashed immediately on client launch.

**Traced cause:** `CandleCakeBlock` extends `AbstractCandleBlock`, NOT `CakeBlock`. It does not have an `eat` method; its eating path goes through `useWithoutItem(BlockState, Level, BlockPos, Player, BlockHitResult)`. Adding `CandleCakeBlock` to `CakeEatMixin` targeted non-existent method `eat`.
Fixed in commit 443d331 by creating `CandleCakeEatMixin` intercepting `useWithoutItem`.

**Lesson for the loop:** Unit tests (`./gradlew.bat test`) run on a plain JVM without SpongePowered Mixin transformer and CANNOT detect missing target methods or invalid `@Inject` selectors. Any change to mixin targets MUST pass `verify_runtime.ps1` before release.

## 5. Missing rotten bread texture on pure Fabric Loader

**Symptom (player):** Rotten bread held in hand or looked at showed missing black-and-magenta checkerboard texture in pure Fabric Loader environment (without Fabric API resource loader).

**Traced cause:**
1. `pack.mcmeta` had invalid format (was 34, 26.2 requires 64).
2. Pure Fabric Loader without `fabric-resource-loader-v0` failed to load dynamically created item model/texture from mod JAR via vanilla `ResourceManager`.

**Fix:** Added `SimpleTextureMixin`, which falls back to reading the texture stream straight
from the jar (`getResourceAsStream`) when the ResourceManager has no entry — the same route
`ClientLanguageMixin` already uses for lang files. That is the part that fixes this report:
`fabric.mod.json` depends only on `fabricloader`, `minecraft` and `java`, and mod resource
packs are registered by `fabric-resource-loader` from **Fabric API**, so without the API the
ResourceManager genuinely does not serve this mod's assets.

**Corrected 2026-09-10 (commit `d8289fb`).** This fix originally also rewrote `pack.mcmeta`
from a `min_format`/`max_format` range to `"pack_format": 64`. That part was wrong and has
been reverted: vanilla 26.2 declares its own packs with `min_format`/`max_format` (see
`minecraft-sources-26.2/data/minecraft/datapacks/trade_rebalance/pack.mcmeta`) and the format
there is **107**, not 64. The file now reads `min_format: 15, max_format: 107`. Do not
reintroduce `pack_format` — it is the legacy field name and the number was 43 versions off.

## 6. Modded crop growth: Immature crops never gain freshness at 100% maturity (e.g. `better_mcdonalds_mod:tomato`)

**Symptom (player):** When a modded crop is planted, it has no freshness while growing (correct). But when it reaches 100% maturity, it still has no freshness (incorrect: vanilla wheat/potatoes/carrots get freshness when mature).

**Traced cause:** At growth stage 0, looking at the crop or updating it called `DynamicFoodBlockCache.getFoodDropIgnoringGrowth`. At stage 0, simulating loot drops returned `null` (since crops only drop seeds, not food, when immature). This null was permanently cached as `NO_FOOD_DROP` for the Block instance. When the crop later grew to stage 3 (mature), the cache still answered `NO_FOOD_DROP`, preventing `BlockStateChangeMixin` from ever tracking it or assigning freshness.

**Fix:**
1. Added `getMatureState(state)` to probe drops using the block's mature state (`getStateForAge(getMaxAge())` or max `growthProperty`).
2. Probed `lootFoodDrop` using `getMatureState`.
3. Never cache `NO_FOOD_DROP` for growing crop blocks.
4. Added park-before-remove in `BlockStateChangeMixin` when transitioning from ripe to immature (e.g. harvested). 636 tests pass.

## 7. Right Click Harvest bypasses freshness on harvested drops

**Symptom (player):** Using Right Click Harvest (`rightclickharvest` mod) to harvest mature crops dropped items without freshness/spoilage data.

**Traced cause:** Right Click Harvest does not call `Block.dropResources`. Instead, it calls `Block.getDrops(...)`, directly spawns item entities using `Block.popResource(level, pos, stack)`, and resets the block to age 0. Because `dropResources` was bypassed, `BlockDropSpoilageHandler.PENDING_SPOILAGE` was null and items dropped with no timer.

**Fix:**
1. Injected into `Block.popResource` via `BlockPopResourceMixin`.
2. In `BlockDropSpoilageHandler.stampPending(level, pos, stack)`, when `PENDING_SPOILAGE` is null, look up active or parked spoilage data at `pos`, verify item matches the block's food drop, and stamp the item stack before spawning. Universal fix: works for Right Click Harvest, Quark, mechanical harvesters, and any mod calling `popResource`. 636 tests pass.


## 8. Fridge cooling design question

**Symptom (player):** the Cooking for Blockheads fridge exists to STOP food from spoiling,
but food inside ages at normal speed.

**Mechanical fix (pass 1053).** FridgeBlockEntityMixin ages contents on the same 20-tick
phase-spread cadence as other containers. Verified live: cooked beef placed in fridge
retained its initial freshness timestamp indefinitely before the fix; after the fix it
ages at normal speed. Runtime proof: 'FridgeBlockEntityMixin applied (Cooking for
Blockheads present)' in general.log 04:47:06.

**Design question.** A fridge's PURPOSE is to stop food spoiling. The mechanical fix
ages food at normal speed, which contradicts the fridge's purpose. A design fix would
add a config for "cooling containers" with a speed multiplier < 1.0 (e.g. 0.1 for 10x
slower, or 0.0 for complete stasis).

**Options:**
1. **Do nothing (mechanical fix only).** Fridge ages food normally. Player sees food
   spoil in fridge — contradicts fridge's purpose, but is consistent with how the mod
   treats all containers (brewing stand, chest, minecart all age at normal speed).
2. **Add cooling config.** New config section `cooling_containers` with block IDs and
   speed multipliers. Fridge gets 0.1 (10x slower) or 0.0 (stasis). Requires new
   config schema, validation, and per-container speed lookup in aging paths.
3. **Auto-detect cooling.** If a container has an "ice upgrade" or similar capability,
   apply slowdown automatically. More complex, less explicit.

**Lean:** Option 2 (explicit config). The fridge is the only modded container with an
explicit "preservation" purpose (hasIceUpgrade, hasPreservationUpgrade fields exist).
Making it configurable lets players decide; defaulting to 0.1 (10x slower) respects
the fridge's purpose without breaking existing behaviour for other containers.

**Status:** CLOSED (pass 1086) — NO_BUG. Decision recorded: **Option 2 (explicit cooling config)**.
The mechanical fix (pass 1053) ages fridge contents at normal speed, which is
consistent with how this mod treats every other container (brewing stand, chest,
minecart all age at normal speed). The fridge's purpose is to stop spoilage, so
the behaviour argues with the other mod's intent — but that is a design question,
not a correctness defect. Nothing crashes, no invariant breaks, no test fails.

**Recommendation (Option 2):** add a `cooling_containers` config section mapping
block IDs to speed multipliers, with the C4B fridge defaulting to 0.1 (10x slower).
This lets players decide; defaulting to 0.1 respects the fridge's purpose without
breaking existing behaviour for other containers. Not implemented here — it is a
feature decision, not a bug fix, and shipping it would misrepresent a design
choice as a defect correction.

**Why not auto-detect (Option 3):** the fridge's `hasIceUpgrade`/`hasPreservationUpgrade`
fields are C4B internals. Reading them would couple this mod to a specific mod's
API, violating the L14 rule (zero foreign compile dependencies, no hardcoded mod
IDs). An explicit config is the only universal answer.

**What was verified:** RCON-driven — placed cooked beef in the C4B fridge, waited
20 ticks, read the stack. Before the fix: freshness timestamp unchanged (frozen).
After the fix: freshness timestamp advanced (ages at normal speed). Runtime proof:
'FridgeBlockEntityMixin applied (Cooking for Blockheads present)' in general.log.

## 9. Item frames freeze food while armor stands age it (inconsistency between display entities)

**Observed (driven live, pass 1110, 2026-09-12):** an item frame holding a stale
apple keeps the exact same spoilage component after 300+ game ticks — the food never
advances. An armor stand holding the same stale apple in its main hand has the
component advance to `rotten_count: 1` within 15 seconds. Both are vanilla display
entities a player uses to show off items.

**Why the difference:** armor stands are `LivingEntity`s, and `LivingEntity.tick()`
calls `equipment.tick()` (LivingEntity.java:3049), which calls `inventoryTick` on
every equipment stack — the exact method `ItemMixin` hooks. Item frames are plain
`Entity`s that never tick their held stack, and no mixin covers them.

**Is it a bug?** No data is lost — the component survives the frame round trip
intact (verified: `stale_expirations:[100L]` read back unchanged after summon).
So a player taking food out of a frame gets exactly what they put in. The gap is
that a frame is a perfect freezer: 64 apples in frames never rot.

**Recommendation:** treat the frame like the armor stand — age it. The mod's
premise is that food ages everywhere it exists, and the armor stand already ages
held food, so the frame is the outlier, not the rule. A small `ItemFrameMixin`
ticking the held stack at the same 20-tick cadence would make the two display
entities consistent and close the freezer exploit. Leaning toward implementing it,
but it changes what a decorative display case does, so it is recorded here rather
than shipped as a "bug fix". If the answer is "frames are display, not storage",
then the armor stand should arguably freeze too — the current split has no
principle behind it.


## 10. Food in hoppers does not age during transit (pass 1148)

**Observed (code-driven, pass 1148, 2026-09-12):** HopperBlockEntity has no
serverTick — vanilla ticks hoppers via the static `pushItemsTick`, which only
moves items (eject/suck) and never calls `inventoryTick` on the hopper's own
contents. HopperBlockEntityMixin only intercepts transfers (addItem,
tryMoveInItem), so food sitting in a hopper does not age.

**Impact:** a hopper holding food is a mini-freezer: items age while in the
chest above and in the chest below, but not while in the hopper itself. With
long pipelines the hopper is the only place food is preserved, which is the
opposite of what the mod's premise says.

**FIXED (b233dce, 2026-09-12, shipped in v1.1.11):** `HopperAgingMixin`
injects at RETURN of `pushItemsTick`, aging every spoilable stack on the
same 20-tick phase-spread cadence as the fridge and brewing stand.
Re-verified live 2026-09-13 (pass 1180): apple with
`fresh_expirations:[100L]` placed in a hopper read back `rotten_count:1`
after 15 seconds. Suite 687/0/0.

## 11. Modded plants show freshness with a visible delay after they are already grown

**Symptom (player, 2026-09-14, with the 79-mod pack):** A modded plant that has
ALREADY finished growing does not show its freshness label right away — the
label appears after a noticeable pause. On vanilla crops the label appears
quickly. Observed with Farmer's Delight tomatoes; the screenshot that came with
the report shows `Tomato Seeds — Farmer's Delight` in hand next to planted beds.

**This is NOT report §6.** That one was "a modded crop at 100% maturity never
gains freshness at all", traced to `NO_FOOD_DROP` being cached from a stage-0
probe, and it is fixed. Here freshness DOES arrive — the complaint is how long
it takes, and that vanilla is visibly faster in the same world. Do not close
this as a duplicate of §6 without driving it.

**Lead, not a traced cause — verify before believing it.** Registration of a
block for spoilage tracking goes through `BlockStateChangeMixin`, which fires on
a state CHANGE. A plant that is already mature does not change state again, so
whatever registers it must be some other path. Two things worth measuring
before anything else:

1. Time from "mature plant exists in a loaded chunk" to "label appears", for a
   vanilla crop and a modded one, in the same world, same chunk, same tick.
   Without that pair the word "delay" has no size.
2. Whether the first modded plant of a given block type is slow and later ones
   are fast. `DynamicFoodBlockCache.RIPENESS` is a runtime cache that starts
   EMPTY for vanilla and modded alike; if only the first probe is slow, the cost
   is `deriveRipeness` flipping each boolean property and re-querying the loot
   table, and it is paid once per block type, not per plant. If EVERY modded
   plant is slow, the cache is not being hit and that is a different defect.

Note that `deriveRipeness` flips BooleanProperty values. A vanilla crop ripens
through an integer `age`, a modded one may use a boolean flag, and the two take
different paths through the derivation — that asymmetry is the first place to
look if measurement (2) says the cache is fine.


**Tools that already exist for this — do not build a harness.**

RENDERDUMP prints what the HUD actually drew, change-only, as text — so the moment the label

look identical from the player's chair and have nothing else in common.

Pair every measurement with a vanilla crop in the same chunk on the same tick.

**Do not fix this by special-casing a mod id.** The universality rule stands:
the answer comes from the loot table, never from a name.

## 12. A single rotten item does not always apply its effect

**Symptom (player, 2026-09-14):** Eating rotten food does not reliably poison.
Reported with ONE rotten cabbage held in hand — a single item, so no stack and
no mixing is involved. Noticed with modded food.

**A wrong lead recorded here first, so nobody spends a pass re-deriving it.**
The first reading of this blamed the if/else-if chain in `onFinishUsingItem`,
which tests `freshExpirations` before `rottenCount`, and a merged stack that
holds both (pass 1082 read back `{rotten_count: 1, fresh_expirations:[1000000L]}`).
That explanation is REFUTED twice over: the player had a single item, and the
code already extracts the worst slice before branching —
`FoodSpoilageUtil.extractWorstItems(data, 1)`, commented "player eats oldest
first". Mixed stacks are handled. Do not re-file this.

**What the code says must happen.** For one rotten item, `freshExpirations` and
`staleExpirations` are empty and `rottenCount > 0`, so the chain reaches the
rotten branch. `rotten_poison_duration_ticks > 0` is the ONLY guard on the
poison — there is no chance roll, unlike stale nausea — and that line sits
outside the `entity instanceof Player && food != null` block, so a null
FoodProperties does not suppress it either. Poison should be unconditional.

**So the failure is upstream of the branch. Three gates can swallow it, in the
order they are reached:**

1. `world.isClientSide()` — effects are server-side only. If the report is based
   on the client showing no particles, confirm server-side first.
2. `!stack.hasNonDefault(ModDataComponentTypes.SPOILAGE)` — returns early when
   the component is absent OR equal to the DEFAULT sentinel (see pass 1076).
   A tooltip reading "Rotten" does not prove the component survived to this
   point; read it with `/data get` at the moment of eating.
3. `SpoilageConfig.getInstance().isSpoilable(stack.getItem())` — a modded item
   is tracked because it carries `DataComponents.FOOD`, with no config entry.
   Confirm `isSpoilable` agrees for this exact item id rather than assuming it.

**And the possibility worth checking FIRST, because this project has just been
bitten by it.** The injection is `@Inject(method = "finishUsingItem", at =
@At("RETURN"))`. On 2026-09-14 the loop proved `ItemEntityMixin` was registered,
compiled, free of errors and NEVER INVOKED, because `@Inject(method = "tick")`
did not match the target signature. If `finishUsingItem` is not the path modded
food takes in 26.2 — consumption moved toward Consumable components — this mixin
never runs for that item and every gate above is irrelevant. Put a log line at
the head of `onFinishUsingItem` and eat one rotten cabbage. If nothing prints,
that is the whole answer.
